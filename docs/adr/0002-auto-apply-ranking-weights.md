# 0002. 因子權重候選自動套用，不設人工審核關卡，靠自動 rollback 補償

## 狀態

已接受（2026-08-24，grill-me 收斂）

## 背景

`src/optimize.py`（Phase 5）的自我定位是「防止自欺的工具，不是找最佳解的工具」——Deflated Sharpe Ratio 與 PBO 兩道門檻算出來之後，2026-08-18 那次搜尋是由人決定「PBO=0.91 超標，不採用」，維持原設定。lighthouse.md Phase 6 要把「持續評估 `finlab_factors.RANKING_WEIGHTS` 候選」的流程排程自動化（每月一次）。第一個要決定的是：排程跑完、候選通過 DSR/PBO/高原寬度門檻之後，誰按下「採用」？

## 決策

不設人工審核關卡：候選只要同時通過 DSR ≥ 0.95、PBO ≤ 0.5、高原寬度 ≥ 搜尋範圍 20%，就自動生效（寫進 `db.py` 的 `meta.active_ranking_weights`，透過 `finlab_factors.composite_scores(weights=...)` 既有的 override 參數生效）。用**自動 rollback** 取代人工審核：套用後的下一個排程週期，若新候選的樣本外表現明顯劣於前一組設定或買進持有，自動退回前一組，事件記進既有的 `optimization_runs` 表。每次排程跑完（採用/維持/rollback 任一結果）都發 Telegram 通知——通知本身不是審核關卡，只是可觀測性。

## 為什麼這樣分界

DSR/PBO 是統計量，本身已經是「用數字取代人工判斷」的機制——8/18 那次人工決定「不採用」，決定的依據就是 PBO 這個數字超標，不是額外的主觀判斷。既有框架的守門邏輯已經是規則化的，人在那個流程裡扮演的角色是「執行規則算出來的結論」，不是「用規則以外的知識做判斷」。把「執行結論」這一步自動化，不算拿掉框架真正依賴的判斷力，只是拿掉一個延遲。

真正的風險不是「規則被拿掉」，而是「規則本身有 bug 時沒人攔」——這個風險用自動 rollback（下一週期表現變差就退回）加上事件留痕來補償，而不是用人工審核補償。

## 考慮過但拒絕的方案

**只通知、不自動套用（人工按下「採用」）。**
grilling 過程中列出的替代方案，使用者明確選了自動套用而不是這個。拒絕理由：手動確認需要使用者固定盯著通知按下同意，而這正是「持續優化」這個需求最初想避免的手動負擔——這條管線目前又是純內部研究管線（見 lighthouse.md Phase 6 範圍界定，`portfolio_backtest.py` 沒有被 `app.py` 引用過），使用者不會有理由每月主動去查通知，"只通知"實質上等於"永遠不套用"。

**自動套用但不設 rollback，只發通知讓人事後手動退回。**
grilling 過程中列出的另一個候選，被「自動 rollback」取代。拒絕理由：套用與發現「表現變差」之間有一個排程週期（一個月）的延遲；若無自動 rollback，這段期間內管線持續用著已經被觀察到變差的設定，直到使用者人工介入。而使用者本來就不會每月主動查——通知很可能被忽略到下下輪才看到。自動 rollback 把「發現變差」與「退回」之間的延遲壓到最短，不依賴使用者的主動性。

**對 `RANKING_WEIGHTS` 三個數值做連續搜尋，而非離散具名候選比較。**
grilling 過程中列出的另一個候選。拒絕理由沿用 Phase 5 文件既有立場：對因子權重做連續搜尋等於在同一批雜訊上重學一次，Phase 4 的 IC/ICIR 顯著性檢定已經是「這個因子有沒有真訊號」的把關，權重數值本身沒有需要精細搜尋的額外自由度。這條決定本次沒有被重新開放討論，直接沿用。

## 影響

- `src/db.py`：新增 `active_ranking_weights` 這個 key 進既有 `meta` 表（`set_meta`/`get_meta`），不需要 schema migration。
- `src/finlab_factors.py`：不變——`composite_scores(weights=...)` 既有的 override 參數直接拿來用，模組維持「純函式、無 I/O」設計。
- 新增 `.github/workflows/optimize.yml`：排程本身即是這個決策的執行者。workflow 失敗/超時如何處理（例如漏跑一個月）不在本 ADR 範圍，留給實作階段的一般性錯誤處理設計。
- 這次調查/決策記錄本身不含程式碼變更，實作留給後續的 build 階段。

## 修訂記錄

- **2026-10-04：閘門的 DSR 對象改為高原勝者。** 權重掃描（`sweep_ranking_weights_walk_forward()`）原本對 point_best（樣本外平均報酬最高者）計算 DSR，但被採用的是高原勝者（逐 fold 勝出最多者），兩者可以不同，使「通過閘門」不保證被採用的候選自己通過 DSR。現在 DSR 改為對高原勝者計算，結果新增 `dsr_of` 欄位標明對象；DSR ≥ 0.95、PBO ≤ 0.5、高原寬度門檻的數值，以及自動套用／rollback 的決策本身不變。依據與歷史重跑影響見 `docs/plan_dsr_target_plateau_winner_2026-10.md`。
